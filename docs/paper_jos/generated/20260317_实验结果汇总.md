## 1A. 设计依据补充说明

### 1A.1 为啥主实验扩成 5 个问题，不是 3 个或者 6 个

这 5 个问题不是按数量凑出来的，而是按“任务类型覆盖”来选的：

1. `Q1` 技术影响力驱动因素分析，对应解释型分析
2. `Q2` 技术融合趋势识别，对应结构/趋势型分析
3. `Q3` 国家/地区竞争态势评估，对应比较评估型分析
4. `Q4` 技术生命周期阶段判断，对应时序阶段判断型分析
5. `Q5` 专利组合风险评估，对应综合风险评估型分析

这样设计的核心依据是：五类问题刚好覆盖了本文最想检验的五种规划需求，即变量锚定、结构趋势识别、跨主体比较、时间演化判断和综合证据闭环。它们对应的数据组织方式、分析方法组合和证据调用逻辑都不一样，因此比只看单一问题族更能检验规划系统是否稳定。

选择 `5` 而不是 `3`，主要是因为 `3` 个问题只能覆盖“解释/趋势/比较”三类基础任务，无法充分暴露“时间阶段判断”和“风险评估”这两类更依赖证据闭环与方法组织的问题，容易把系统评价收缩成早期冻结版 `Q1-Q3` 的延长线。

选择 `5` 而不是 `6`，主要是因为 `5` 已经达到“覆盖足够广且彼此区分明确”的平衡点；再加第 `6` 类问题，大概率会和现有五类中的某一类高度重叠，但每增加 `1` 个主问题，就要额外增加 `6 模式 × 1 问题 × 5 重复 = 30` 组内部实验，以及 `2 模式 × 1 问题 × 5 重复 = 10` 组外部基线实验，成本会明显上升，而新增信息量未必成比例。

### 1A.2 外部基线为啥选这两个，它们分别代表什么

外部基线没有追求“基线越多越好”，而是有意选了两条最有代表性的 literature-inspired 机制路线，并且两者都能在统一接口下与本文系统直接比较。

- `G_react_single_agent` 代表“单智能体、一次性、问题语义驱动”的路线。它对应的是 ReAct-style 的常见做法：把推理与行动放在一个 agent 里，让系统依靠通用推理能力直接产出方案，但不显式引入数据感知模块和知识约束模块。
- `H_execution_feedback` 代表“单智能体 + 执行反馈再规划”的路线。它保留了两轮执行反馈，但仍不使用数据感知和知识图谱，检验的是“只靠 feedback loop，是否已经足够接近完整系统”。

之所以选这两个，是因为它们刚好构成一组清晰对照：`G` 检验“不给外部结构，只靠单智能体一次性规划行不行”，`H` 检验“在单智能体框架里加入执行反馈后是否就足够”。如果这两条路线都明显弱于 `C_iterative`，就能更清楚地说明本文优势不只是“多跑一轮”或“换个 agent 写法”，而是来自数据感知、知识约束和迭代闭环这三者的协同。

### 1A.3 为啥选择 Bugzilla 做跨域数据

跨域数据没有选成完全不同任务形态的数据，而是选了 Bugzilla 缺陷数据，原因是它一方面与专利分析在领域语义上明显不同，另一方面又保留了结构化分析任务所需要的核心数据形态：文本字段、类别字段、时间字段和组织/责任字段同时存在。这使它适合检验“规划框架是否能迁移”，而不是把失败简单归因于任务接口完全换了。

当前物化后的 `cross_domain_bugzilla` 基本统计如下：

- 数据源为标准化后的 Mozilla Bugzilla 缺陷数据
- 共 `3000` 条记录、`12` 个字段、`1` 个工作表
- 字段包括 `title`、`description`、`severity`、`component`、`product/project`、`created_at`、`resolved_at`、`reporter`、`assignee`、`status`、`priority`、`comments_count`
- `product/project` 共 `6` 类，每类 `500` 条：`WebExtensions`、`Toolkit`、`Firefox for Android`、`Firefox`、`DevTools`、`Core`
- 时间跨度为 `2024-01-12` 到 `2026-03-15`
- `1323` 条记录有 `resolved_at`，`1677` 条尚未关闭；已关闭样本的解决周期中位数约为 `6` 天
- 共涉及 `740` 位 `reporter`、`289` 位 `assignee`
- `comments_count` 均值约 `5.08`，中位数为 `4`

这组数据适合作为跨域小验证，还有一个现实原因：它已经具备较好的结构可比性。专利数据和缺陷数据虽然语义不同，但都需要系统同时处理文本线索、分类标签、时间演化和跨主体比较，因此能较公平地检验规划能力是否能在异域数据上保留。

### 1A.4 为啥跨域只选 3 个问题、2 个模式

跨域实验的定位是“真跨领域初步验证”，不是第二套完整主实验，所以它采用的是最小但有解释力的设计。

只选 `3` 个问题，是因为 Bugzilla 数据能够稳定支撑的跨域问题主要就是三类：

1. 缺陷影响因素分析，对应 `severity/priority/status/component/comments_count`
2. 缺陷与模块演化趋势识别，对应 `component/product + created_at/resolved_at`
3. 项目或组件质量差异评估，对应 `product/project/component/status`

没有继续照搬主实验的 `Q4/Q5`，是因为“技术生命周期阶段判断”和“专利组合风险评估”带有明显的专利场景语义，强行映射到 Bugzilla 容易把评测变成提示词改写问题，而不是框架迁移能力问题。

只选 `D_baseline0` 和 `C_iterative` 两个模式，是因为跨域节要回答的核心问题非常集中：当数据从专利切换到软件缺陷时，“无机制基线”和“完整框架”之间是否仍有明显差距。这里不需要像主实验那样做细颗粒度机制归因，只需要保留最弱基线和完整系统的对照即可。这样实验规模为 `2 模式 × 3 问题 × 3 重复 = 18` 组；如果扩成全部 `6` 模式，同样口径下会变成 `54` 组，成本和解释复杂度都会明显上升，而且会把“跨域有效性”与“跨域内部归因”混在一起。

## 2. 主实验结果

主实验新版 `LLM-as-Judge` 总分如下（mean ± std）：

| 模式              | 总分             |
| --------------- | -------------- |
| `C_iterative`   | `23.80 ± 2.12` |
| `F_ablate_kg`   | `23.12 ± 2.17` |
| `E_ablate_data` | `21.72 ± 2.01` |
| `B_data_aware`  | `18.80 ± 3.03` |
| `A_template`    | `16.56 ± 2.36` |
| `D_baseline0`   | `16.16 ± 1.86` |

自动指标与该排序一致：

- `B_data_aware` 的针对性引用数为 `8.44 ± 4.74`，明显高于 `A_template` 的 `1.88 ± 2.33` 和 `D_baseline0` 的 `0.92 ± 1.12`
- `C_iterative` 的方法多样性为 `5.12 ± 0.67`，任务数为 `5.16 ± 0.75`，显著高于单轮方案
- `E_ablate_data` 去掉数据感知后，针对性下降到 `3.80 ± 3.25`
- `F_ablate_kg` 与 `C_iterative` 接近，说明知识图谱收益具有任务依赖性

## 3. 主实验统计结论

新版统计检验基于 `n=25` 配对样本，结果比早期 `n=15` 更稳定。

显著成立的比较：

- `B_data_aware > A_template`
- `B_data_aware > D_baseline0`
- `C_iterative > B_data_aware`
- `C_iterative > E_ablate_data`

未达到显著的比较：

- `C_iterative vs F_ablate_kg`

这意味着当前可以比较稳妥地写出以下结论：

1. 数据感知带来稳定显著收益
2. 迭代机制继续显著提升完整系统表现
3. 知识图谱贡献存在，但具有任务依赖性，不能写成“移除图谱整体更优”

## 4. 外部机制基线结果

外部机制基线设置为：

- `G_react_single_agent`
- `H_execution_feedback`

新版 `LLM-as-Judge` 结果如下：

| 模式                     | 总分             |
| ---------------------- | -------------- |
| `H_execution_feedback` | `21.24 ± 3.26` |
| `G_react_single_agent` | `15.16 ± 3.09` |

当前 strongest external mechanism baseline 为：

- `H_execution_feedback`

与完整系统比较：

- `C_iterative > G_react_single_agent`，差异显著
- `C_iterative > H_execution_feedback`，差异显著

因此，完整系统不仅优于内部弱化版本，也优于两条代表性的外部机制基线。

## 5. 跨领域小验证（Bugzilla）

### 5.1 数据说明

跨领域验证使用的是软件工程缺陷数据，而不是专利数据。

数据集名称：

- `cross_domain_bugzilla`

数据文件位置：

- `outputs/jos_artifacts/datasets/cross_domain_bugzilla.xlsx`

数据来源是 Bugzilla 缺陷跟踪系统，核心字段包括：

- `title`
- `description`
- `severity`
- `component`
- `product/project`
- `created_at`
- `resolved_at`
- `reporter`
- `assignee`
- `status`
- `priority`
- `comments_count`

基本统计信息：

- 共 `3000` 条缺陷记录，`12` 个字段
- `product/project` 共 `6` 类，每类 `500` 条，分布均衡
- 时间跨度为 `2024-01-12` 到 `2026-03-15`
- `1323` 条记录已解析到 `resolved_at`，其余 `1677` 条仍处于未关闭或未解析完成状态
- `comments_count` 均值约 `5.08`，中位数为 `4`
- 共涉及 `740` 位报告者和 `289` 位指派者

选择这组数据而不是别的跨域数据，主要是因为它与主数据集在领域语义上已经明显不同，但仍保留了结构化分析规划所需要的文本、类别、时间和责任主体四类核心信息，因此能更干净地检验框架的跨域稳健性。

对应的 3 个跨领域问题为：

1. 缺陷严重性或问题影响因素分析
2. 缺陷类型与模块演化趋势识别
3. 项目或组件质量差异评估

这 3 个问题是按“可被当前字段稳定支撑的分析类型”来选的，而不是简单把主实验 `Q1-Q5` 原样搬过去。它们分别对应解释型、趋势型和比较评估型三类结构化分析任务；相比之下，主实验中的“生命周期阶段判断”和“组合风险评估”带有更强的专利语义，不适合直接映射到 Bugzilla。

### 5.2 结果

`LLM-as-Judge` 总分如下：

| 模式            | 总分             |
| ------------- | -------------- |
| `C_iterative` | `24.44 ± 1.33` |
| `D_baseline0` | `15.89 ± 2.93` |

统计结果：

- `C_iterative > D_baseline0` 的 `llm_total` 显著
- `specificity_references` 在该数据上不显著

解释：

- 这组数据已经足以支持“框架在软件工程结构化缺陷分析场景下仍保持明显优势”的谨慎结论
- 但它仍应被表述为“小规模跨领域初步验证”，不宜夸大为强泛化证明
- `specificity_references` 这个自动指标本身更偏专利/数值引用型表达，因此在 Bugzilla 上不能作为核心判断依据

## 6. 当前最稳妥的论文结论

如果压缩成一段总述，当前可以写为：

> 完整系统 `C_iterative` 在内部机制归因、外部机制对比和跨领域初步验证三层证据上均取得最佳或最稳定表现。其中，数据感知是最稳定、最明确的性能来源，迭代机制决定系统上限，而知识图谱的收益具有任务依赖性，应作审慎解释。

更具体地说：

- `C_iterative` 是当前总体最优方案
- `B_data_aware` 是稳定显著优于基础方案的关键增益来源
- `A_template` 不能写成稳定优于 `D_baseline0`
- `F_ablate_kg` 不能写成整体优于 `C_iterative`
- `H_execution_feedback` 是当前最强外部机制基线，但仍显著弱于完整系统
- Bugzilla 结果支持“跨领域初步有效”，但不支持夸大到强泛化

## 7. 当前不建议写进论文的结论

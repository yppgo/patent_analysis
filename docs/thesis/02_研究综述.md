第二章 研究综述

2.1 LLM 驱动的自动化数据分析研究进展

LLM 驱动的数据分析系统近年来快速发展，推动了数据科学工作流从人工操作向自动化编排演进[19][20]。代表性工作显示，多智能体机制可把复杂数据分析过程拆分为"任务规划、代码执行、结果解释"等子环节，从而提高自动化完成率。

DS-Agent[16] 通过案例推理（Case-Based Reasoning, CBR）从 Kaggle 历史任务库中检索相似案例，利用迁移策略指导 LLM 生成数据科学代码。该方法显著增强了任务求解的可复用性，但其核心依赖在于历史案例库的覆盖度，在跨领域或数据分布显著变化时可能失效。Data Interpreter[17] 通过"动态规划—代码执行—反馈迭代"循环增强了代码执行的稳定性和正确率，是当前 LLM 数据科学 Agent 中执行层能力最强的系统之一。Data-to-Dashboard[18] 面向企业分析场景，通过多角色协同生成可视化仪表板，展示了 LLM Agent 在商业分析中的应用前景。此外，相关综述指出，统计与数据科学场景中的 LLM Agent 生态正在形成，系统能力正从"单模型问答"向"任务编排执行"演进[19]。

尽管如此，现有研究仍主要优化"执行层"，对"规划层"的研究不足。所谓执行层，关注的是给定任务后如何正确产出代码和结果；而规划层要解决的是"应该分析什么、为何这样分析、哪些变量需要控制"。在科研型数据分析中，规划层质量往往决定最终结论质量。若规划阶段缺乏数据证据，后续执行再稳定，也可能只是"稳定执行了不够好的方案"。

另一个共性问题是"历史案例依赖"与"当前数据脱钩"。DS-Agent 使用历史任务库强化迁移能力，但在跨领域或数据分布显著变化时，历史最优方案未必适配当前数据。Data Interpreter 的动态规划虽然在执行过程中根据代码反馈调整策略，但规划的起点仍是问题语义而非数据事实——系统并未在规划前对数据的变量分布、跨列关系和结构特征进行系统性探测。专利分析场景中这一问题更突出：字段语义与技术背景强耦合，指标解释需要结合领域上下文，模板迁移风险较高。

从"规划是否感知数据"这一维度审视现有系统，可以将其分为两类：**数据无关规划**（data-blind planning）和**数据感知规划**（data-aware planning）。前者仅依据问题语义和历史经验生成分析方案，代表工作包括 DS-Agent 的案例检索和通用 LLM 的直接指令生成；后者在规划前显式探测当前数据特征，将数据事实作为方案设计的输入约束。现有系统中，Data-to-Dashboard[18] 通过多轮对话让用户补充数据信息，具有隐式的数据感知特征，但其感知过程依赖人工交互而非自动化提取，且仅面向可视化而非统计分析。综合来看，针对科研级数据分析的自动化数据感知规划机制目前仍处于空白状态。

2.2 多智能体协作框架研究进展

多智能体系统为 LLM 应用提供了结构化的协作范式。ReAct[9] 提出将推理（Reasoning）与行动（Acting）在语言模型中交替执行，建立了 LLM Agent 的基本行为模式：先思考再执行、根据环境反馈调整策略。这一范式为后续多智能体架构奠定了基础。

在多智能体协作框架方面，AutoGen[11] 提出基于多智能体对话的编程范式，支持灵活定义 Agent 角色、交互规则和终止条件，已在代码生成、数学推理等任务中展示了多 Agent 协作的优势。MetaGPT[12] 引入"标准作业程序"（SOP）概念，将软件工程的角色分工（产品经理、架构师、工程师）映射到 LLM Agent 协作流程中，通过结构化中间产物传递信息、减少幻觉。CAMEL[13] 通过角色扮演和引导式对话实现两个 LLM Agent 之间的自主合作，探索了无人干预情况下的协作涌现能力。

在工程实现层面，LangChain[14] 提供了 LLM 应用的基础组件库（提示模板、工具调用、检索增强等），LangGraph[15] 在其基础上引入有向图状态机机制，支持循环、分支和条件路由，适合编排需要多步决策和反馈循环的复杂工作流。相较于 AutoGen 的对话驱动模式，LangGraph 的状态机模式在流程可控性和中间状态可追踪性方面具有优势[10]。

综合来看，当前多智能体框架已解决了"如何让多个 Agent 协作"的基础工程问题，但在"Agent 应该做什么决策"层面仍高度依赖提示词设计。对于数据分析场景，现有框架提供了协作骨架，但缺少数据感知和领域知识注入的内建机制。

2.3 LLM 在专利分析与知识图谱增强中的应用进展

LLM 与专利任务的结合已经从早期摘要生成拓展到问答与语义检索。EvoPat[21] 通过多 LLM Agent 实现专利摘要、比对与评估流程，利用 RAG 检索增强和子任务分解策略提升处理效果。KLIPA[22] 引入知识图谱增强专利问答和信息获取，将结构化知识与非结构化文本检索相结合。与此同时，专利 NLP 综述持续指出，专利文本处理仍是当前研究主流，涵盖分类、检索、实体识别、语义匹配等任务[23]。

这些进展证明了 LLM 在"专利文本理解"上的价值，但仍难直接替代"专利计量分析"。原因在于，计量分析的关注对象是结构化数据中的变量关系、时间演化与机制识别，需要构建完整统计分析链条，包括变量测量、模型选择、混杂控制与稳健性检验[1][2][4]。该链条与文本问答的技术路径差异显著。

已有研究也提示，专利分析正从单点文本任务向多维度融合任务演进，亟需将文本、结构字段、网络关系和统计建模统一到一个可执行框架中[6][7]。因此，面向专利结构化数据的"方案级自动化"仍然是关键空白。

2.3.1 知识图谱增强 LLM 研究进展

知识图谱增强 LLM 的核心目标是将外部结构知识引入生成过程，以提升一致性、可解释性和事实正确性[25][26]。GraphRAG[24] 通过"局部检索 + 全局社区结构"提高了复杂问题回答质量，展示了图结构在长上下文组织中的优势。相关综述进一步指出，知识约束在降低幻觉和提升推理稳定性方面有明显潜力[27]。

但从应用目标看，当前多数 KG+LLM 工作仍聚焦检索问答，知识图谱主要作为"信息源"而非"决策器"。对于数据分析任务，方案质量不仅受知识完整性影响，更受数据可用性和方法可执行性影响。若知识约束过强而缺乏数据证据校准，系统可能陷入"结构正确但数据适配不足"的状态。

在更广泛的 LLM 科学发现方向，AI Scientist v2[28] 实现了从假设生成到实验执行到论文撰写的全自动科研流程。EMNLP 2025 的 LLM 科学发现综述[29] 定义了三个自主水平：Level 1（LLM as Tool）、Level 2（LLM as Analyst）、Level 3（LLM as Scientist）。这些工作表明 LLM 正在从辅助工具向自主分析者演进，但现有 Level 2 系统普遍缺少数据感知和领域知识图谱两个关键组件。

2.4 研究现状总结与本文定位

综合前述综述，现有研究存在三类共性不足，且每类不足对应本文的一项研究内容：

（1）在 LLM 自动化分析方向，执行优化多、规划优化少，缺乏"规划前数据感知"机制。本文通过 DataPreview、GraphPreview 与洞察生成三层输入，将数据证据前移至规划阶段，解决该不足。

（2）在 LLM 专利应用方向，文本处理多、结构化计量少，缺少端到端方案生成系统。本文构建面向专利结构化数据的四智能体系统，覆盖从问题输入到分析输出的完整流程。

（3）在 KG+LLM 方向，检索问答多、分析引导少，缺乏"知识约束 + 数据证据"协同框架。本文提出双知识图谱协同机制，并通过实验验证知识约束的增益边界条件。

上述定位使第二章与后续章节形成清晰映射：第二章提出问题缺口，第三至六章给出系统实现与实验验证，第七章总结贡献与边界条件。

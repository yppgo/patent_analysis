# 第四章 系统原型实现

## 4.1 系统架构与技术选型

本系统以 Python 为核心实现语言，使用 LangGraph[15] 组织多智能体状态机流程，并采用"双模型分工"策略：通义千问（Qwen）负责规划和评审，Claude 负责代码生成和执行修复。该组合的工程出发点是将"文本规划稳定性"和"代码生成能力"分开优化，降低单模型在全流程任务中的能力短板[20][31]。

系统主模块对应如下代码路径：工作流编排在 `src/core/workflow.py`，规划模块在 `src/agents/strategist.py`（约 1520 行），方法规格化模块在 `src/agents/methodologist.py`，执行模块在 `src/agents/coding_agent_v4_2.py`，评审模块在 `src/agents/reviewer.py`。数据感知由 `src/utils/data_preview.py`（602 行）与 `src/utils/graph_preview.py`（451 行）提供，知识约束由 `src/graphs/causal_graph_query.py` 与 `src/graphs/method_graph_query.py` 提供。

从工程职责角度，系统采用"规划—规格—执行—评审"四段式流水线，每段均有结构化 JSON 输入输出，整体架构参见图 3-1。该设计使系统不仅能产出结果，也能产出中间证据链，便于复核与追踪[12][15]。

## 4.2 系统核心模块实现

DataPreview 的目标是把"数据事实"前置到方案规划阶段。模块输入为 pandas DataFrame，输出为结构化预览对象，包含列类型画像、基础统计、跨列统计和抽样摘要四部分。

### 4.2.1 列语义识别与类型画像

系统首先识别数值列、分类列、日期列和文本列，并为每列生成质量摘要（缺失率、唯一值数、分布形态）。为解决专利数据集列名为中文且含括号的问题，模块内置了一套列语义映射表，覆盖 30 余个常见专利字段，将列名映射为分析语义描述。例如：

| 原始列名 | 语义描述 |
|---------|---------|
| 被引用专利数量 | 被引用次数（数值维度，反映专利影响力） |
| IPC分类号 | 国际专利分类号（技术维度，多值分隔符 \|，可用于技术分类、聚类、共现网络） |
| 发明人 | 发明人（实体维度，多值分隔符 \|，可用于合作网络分析、团队规模统计） |
| 法律状态/事件 | 法律状态（分类维度，如"授权"、"授权\|权利转移"等） |

该映射表使后续 LLM 在生成分析方案时能够直接理解每列的分析用途，避免因列名歧义导致的错误。

### 4.2.2 跨列统计关系抽取

跨列统计是 DataPreview 的核心功能，用于自动发现数据中的变量关系线索。模块实现三类跨列统计：

**（1）数值列 Pearson 相关系数**。对所有数值列两两计算相关系数，过滤 |r| > 0.1 的显著关联，按绝对值降序保留前 20 对。该步骤的作用是为后续假设生成提供"哪些变量之间存在线性关联"的定量线索。

**（2）分类列分组对比**。对低基数分类列（唯一值 ≤ 50），按 Top 5 类别分组计算核心数值列均值差异。例如，按"法律状态"分组计算"被引用专利数量"的均值差异，可以发现"授权|权利转移"状态的专利平均被引量是否高于普通授权专利。

**（3）时间趋势检测**。自动检测日期列，按年聚合计算核心数值列的年度均值趋势。该信号可用于发现被引量的时间衰减效应等。

跨列统计的处理流程如算法 4-1 所示，整体数据流见图 4-1：

```text
Algorithm 4-1 CrossColumnStatistics(df, profile)
输入: DataFrame df, 列类型画像 profile
输出: 跨列统计结果 result

1:  numeric_cols ← 从 profile 中提取所有数值列
2:  // 相关系数计算
3:  corr_matrix ← df[numeric_cols].corr(method='pearson')
4:  pairs ← 提取 |r| > 0.1 的列对，按 |r| 降序排列，取前 20 对
5:  result.correlation_pairs ← pairs
6:  // 分组对比
7:  cat_cols ← 从 profile 中提取唯一值 ≤ 50 的分类列（取前 5 个）
8:  core_numeric ← 排除 ID 类列的数值列（取前 3 个）
9:  for each cat_col in cat_cols do
10:   top_cats ← cat_col 出现频率最高的 5 个类别
11:   for each num_col in core_numeric do
12:     grouped_means ← df[cat_col ∈ top_cats].groupby(cat_col)[num_col].mean()
13:     result.group_comparisons.append({group_by, metric, values})
14: // 时间趋势
15: date_col ← 检测含日期关键词的列
16: years ← pd.to_datetime(date_col).dt.year
17: for each num_col in core_numeric do
18:   yearly_means ← df.groupby(years)[num_col].mean()
19:   result.time_trends.append({metric, by_year})
20: return result
```

### 4.2.3 内容样本的分层抽样

为让 LLM 了解专利的技术内容分布，模块按 IPC 分部（首字符 A-H）对摘要进行分层抽样，每部最多采 5 条、总计不超过 30 条，每条截断至 300 字符。使用固定随机种子（random_state=42）保证可复现。相比随机抽样，分层抽样确保各技术领域均有代表性样本，降低了主题偏置。

### 4.2.4 图结构预览模块（GraphPreview）

GraphPreview 用于捕捉 DataPreview 难以表达的网络结构信息。专利数据中存在大量多值关系字段（如 IPC 分类号、发明人、引用专利），这些字段天然可以构建为图，揭示共现关系和协作模式。

#### 4.2.4.1 自动图构建策略

模块首先扫描 DataFrame 中所有含分隔符的列，将其识别为"可构图候选列"。随后通过元素类型分类器判断列内元素的类型，决定构建何种图，自动构图逻辑如图 4-2 所示。分类器对采样元素进行正则匹配和启发式判断：

- 若元素匹配专利编号模式（如 CN120822531A），构建**引用网络**
- 若元素匹配分类码模式（如 G06F21/60），构建**共现网络**
- 若元素为短文本且不含斜杠，判定为人名，构建**合作网络**

在实测中，系统从数据集自动构建了 6 个图：发明人合作网络、IPC 共现网络、引用网络等。

#### 4.2.4.2 分层图算法策略

为兼顾信息密度与计算性能，模块采用分层计算策略。当图规模较小时（节点数 ≤ 10,000），完整计算以下指标：

- **Louvain 社区检测**：使用 python-louvain 库，固定 random_state=42，输出社区数量、各社区规模和每社区 Top 3 代表节点
- **介数中心性**：对大图使用 k=500 近似采样降低复杂度，输出 Top 10 桥梁节点
- **连通分量统计**：输出最大连通分量占比和孤立节点数
- **度分布统计**：输出平均度、最大度和度分布分位数

当图规模超过阈值（LARGE_GRAPH_THRESHOLD = 10,000）时，跳过社区检测和介数中心性计算，仅保留度分布统计，避免 O(n²) 级操作导致规划阶段阻塞。

```text
Algorithm 4-2 GraphPreviewGenerate(df)
输入: DataFrame df
输出: 图结构指标集合 metrics

1:  candidate_cols ← 检测含分隔符(|)的列
2:  for each col in candidate_cols do
3:    elem_type ← ClassifyElements(col)  // patent_id | classification | name
4:    G ← BuildGraph(col, elem_type)     // 构建对应类型的图
5:    if |V(G)| > 10000 then
6:      metrics[G] ← {degree_distribution}        // 仅度分布
7:    else
8:      communities ← Louvain(G, random_state=42)
9:      centrality ← BetweennessCentrality(G, k=500)
10:     components ← ConnectedComponents(G)
11:     metrics[G] ← {communities, centrality, components, degree_distribution}
12: return metrics
```

模块的关键设计原则是**只输出结构化事实，不做语义解读**。例如，输出"节点 H04L9/40 的介数中心性为 0.31"，而不输出"H04L9/40 是技术桥梁"——后者的判断由 LLM 在洞察生成阶段完成。

### 4.2.5 数据洞察生成机制

数据洞察生成是数据感知方案的核心环节，由 Strategist 中的 `_generate_data_insights()` 方法实现。该方法将 DataPreview 与 GraphPreview 的输出合并为 LLM 提示词，驱动 LLM 生成结构化的可检验洞察。

#### 4.2.5.1 洞察生成的 Prompt 设计

Prompt 包含三层输入和严格的输出约束：

**输入层**：
1. 数据统计特征（来自 DataPreview 的相关系数、分组对比、时间趋势）
2. 图结构分析（来自 GraphPreview 的社区、中心性、连通分量）
3. 领域摘要样本（来自分层抽样的 20-30 条专利摘要）

**约束层**：
- 每条洞察必须引用输入中的具体数字
- 每条洞察必须指定可验证的数据列和分析方法
- 洞察分三类：统计信号型（statistical）、图结构型（graph_structural）、内容驱动型（content_driven）
- 禁止常识性结论

**输出格式**：每条洞察包含 7 个字段：

| 字段 | 含义 |
|------|------|
| id | 洞察编号（如 I1, I2） |
| type | 洞察类型（statistical / graph_structural / content_driven） |
| title | 洞察标题 |
| observation | 具体数据观察（必须引用数字） |
| hypothesis | 可检验假设 |
| data_columns | 涉及的数据列名 |
| analysis_method | 建议的分析方法 |

#### 4.2.5.2 洞察示例

在 Q1（技术影响力驱动因素分析）实验中，系统生成的洞察包括：

> **I2**（statistical）：近年授权专利被引量骤降——反映技术迭代加速，需在分析中控制专利年龄，否则会混淆真实影响力。

> **I3**（graph_structural）：H04L9/40 为核心枢纽——可限定分析范围至该 IPC 主导的子网络，提升假设检验的针对性。

这些洞察将作为 Strategist 生成 DAG 蓝图的关键输入。

### 4.2.6 双知识图谱实现

系统使用两类图谱协同约束分析方案的"假设空间"和"方法空间"[25][26]。

#### 4.2.6.1 因果图谱

因果图谱编码了专利计量领域的核心变量关系，包含 30 个变量和 99 条因果路径，局部示例如图 4-3 所示。变量涵盖技术强度、企业规模、研发投资、技术多样性、技术影响力、商业价值等维度。

图谱提供 6 种假设生成策略模板：

| 策略 | 核心思路 | 示例 |
|------|---------|------|
| 理论迁移 | 将已验证理论应用到新场景 | 将"研发投资→技术产出"路径迁移至专利数据 |
| 路径探索 | 发现文献中未充分研究的因果路径 | 探索技术多样性→商业价值的间接路径 |
| 边界条件 | 为已知关系寻找调节变量 | 企业规模是否调节技术多样性与影响力的关系 |
| 中介机制 | 揭示 X → M → Y 的中介效应 | 技术多样性是否通过技术成熟度中介影响商业价值 |
| 反事实推理 | 生成反直觉假设 | 技术多样性高的专利影响力反而更低？ |
| 交互效应 | 探索多变量联合作用 | 研发投资与技术多样性的交互项是否显著 |

#### 4.2.6.2 方法图谱

方法图谱包含 86 种以上的分析方法，按两个维度组织：

- **变量测量方法**（variable_measurement_methods）：为每个变量 ID 提供推荐的量化方式
- **统计分析方法**（statistical_analysis_methods）：按类型分为回归分析（regression）、中介分析（mediation）、调节分析（moderation）

方法匹配逻辑：根据假设类型自动推荐适配的分析方法，匹配示例如图 4-4 所示。例如，中介效应假设自动匹配 Bootstrap 中介检验方法；调节效应假设自动匹配层次回归方法。

#### 4.2.6.3 双图谱协同流程

在 Strategist 中，双图谱的使用顺序为：先由因果图谱生成候选假设（确定"研究什么"），再由方法图谱匹配执行方法（确定"怎么做"）。该顺序保证先确定理论合理的研究方向，再确定技术可执行的实现路径。

### 4.2.7 分析蓝图生成与执行闭环

#### 4.2.7.1 DAG 蓝图结构

Strategist 输出的蓝图为有向无环图（DAG），每个节点代表一个分析任务。任务节点包含以下字段：

```json
{
  "task_id": "task_1",
  "task_type": "hypothesis_test",
  "question": "技术跨界度对技术影响力是否有负向影响？",
  "description": "在H04L9/40子群中进行多元回归...",
  "input_variables": [],
  "output_variables": ["result_1"],
  "dependencies": [],
  "implementation_config": {
    "data_source": "data/new_data.XLSX",
    "sheet_name": "sheet1",
    "columns_to_load": ["IPC分类号", "被引用专利数量", "授权日"],
    "parameters": {
      "core_ipc": "H04L9/40",
      "control_vars": ["patent_age", "legal_status_dummies"]
    },
    "output_format": "json",
    "output_file": "outputs/task_1_result.json"
  }
}
```

节点间通过 `dependencies` 字段和 `input_variables`/`output_variables` 字段建立依赖关系，确保任务按正确顺序执行。

#### 4.2.7.2 方法规格化（Methodologist）

Methodologist 将蓝图节点进一步转化为技术规格，包括函数签名、输入契约、变量约束、参数说明与预期输出类型。该步骤的作用是在 Strategist 的高层规划和 CodingAgent 的底层执行之间建立精确的"合同"。

#### 4.2.7.3 代码执行与纠错（CodingAgent）

CodingAgent 基于技术规格自动生成 Python 代码并在沙箱环境中执行，执行与纠错流程如图 4-5 所示。若执行失败（如缺列、类型错误、统计包调用异常），系统根据错误信息触发定向修复，最多迭代 15 轮。在实验中，所有任务最终均执行成功（成功率 100%），说明该纠错机制具有足够的容错能力。

#### 4.2.7.4 结果评审（Reviewer）

Reviewer 对执行结果进行两个维度的评审：结构完整性检查（输出是否包含预期字段）和语义有效性评估（结论是否回答了研究问题）。评审结果用于最终报告生成。

### 4.2.8 两轮迭代机制

两轮机制通过 `round`、`previous_results` 等参数传递上下文，由 `_generate_refined_blueprint()` 方法实现第二轮蓝图生成。

#### 4.2.8.1 第二轮蓝图生成流程

第二轮 Prompt 包含三个额外输入：
1. 第一轮各任务的执行结果摘要（关键发现、统计量、结论）
2. 差距分析：评估第一轮"已回答"和"未充分回答"的问题边界
3. 深化策略：补充控制变量、增加交互项检验、引入非线性模型

```text
Algorithm 4-3 TwoRoundPlanning(goal, data)
输入: 用户研究目标 goal, 数据集 data
输出: 两轮分析结果 final_results

1:  // 第一轮：探索性分析
2:  insights ← GenerateDataInsights(data, goal)
3:  blueprint_1 ← Strategist(goal, data, insights, round=1)
4:  results_1 ← Execute(blueprint_1)  // Methodologist → CodingAgent → Reviewer
5:  // 第二轮：验证性分析
6:  gap ← AnalyzeGap(results_1, goal, insights)
7:  blueprint_2 ← Strategist(goal, data, insights, round=2,
8:                            previous_results=results_1, gap=gap)
9:  results_2 ← Execute(blueprint_2)
10: final_results ← Merge(results_1, results_2)
11: return final_results
```

#### 4.2.8.2 迭代效果

与单轮流程相比，两轮机制将系统行为从"一次性生成"改为"反馈驱动生成"。实验中，第二轮常见的新增操作包括：负二项回归替代 OLS（非线性建模）、BERT 主题建模（文本挖掘）、IPC 共现网络特征工程（图结构利用）、交互项检验（机制验证）。这些操作将分析从效应发现提升至机制解释层次。

## 4.3 本章小结

本章给出了系统原型的实现细节与关键工程策略。DataPreview 通过跨列统计和分层抽样将数据事实结构化；GraphPreview 通过自动图构建和分层算法策略提取网络特征；数据洞察生成通过约束性 Prompt 将事实转化为可检验假设；双知识图谱通过 6 种策略模板和方法匹配机制实现假设引导和方法约束；两轮迭代通过差距分析驱动深度提升。上述模块共同构成可复核、可迭代的自动分析闭环，为后续实验验证提供了技术基础。
